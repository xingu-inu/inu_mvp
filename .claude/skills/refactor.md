# Code Refactoring

## Iron Law

```
REFACTORING = CHANGING STRUCTURE WITHOUT CHANGING BEHAVIOR
ALL TESTS MUST PASS BEFORE AND AFTER
```

리팩토링과 기능 변경을 동시에 하지 않음. 별도 커밋.

## When to Use

- 코드 가독성/유지보수성 개선이 필요할 때
- 새 기능 추가 전에 구조를 먼저 정리할 때
- 코드 리뷰에서 구조 문제가 지적됐을 때
- 기술 부채를 줄이고 싶을 때

## Pre-Refactoring Checklist

리팩토링 시작 전 반드시:

1. **테스트 상태 확인:**

   ```bash
   npm run test && npm run type-check
   ```

   실패하는 테스트가 있으면 먼저 수정하거나 리팩토링 범위에서 제외.

2. **리팩토링 목표 명확히:**
   - 무엇을 개선하는가? (가독성? 재사용성? 성능?)
   - 어디까지 건드리는가? (범위 제한)
   - 완료 기준은?

3. **변경 범위 파악:**
   - 영향받는 파일 목록
   - 의존하는 컴포넌트/모듈
   - 공개 API 변경 여부

## The Process

### Step 1: 작은 단위로 분리

한 번에 하나의 리팩토링만. 여러 리팩토링을 묶지 않음.

```
OK: "함수 추출" → 테스트 → 커밋 → "변수 이름 변경" → 테스트 → 커밋
NO: 함수 추출 + 변수 이름 변경 + 파일 이동 → 한번에 커밋
```

### Step 2: 각 변경 후 검증

```bash
npm run test && npm run type-check
```

실패 시 바로 롤백하거나 수정. 다음 리팩토링으로 넘어가지 않음.

### Step 3: 자주 커밋

각 리팩토링 단위마다 커밋. 문제 생기면 쉽게 되돌릴 수 있도록.

## Code Smell Checklist

리팩토링 대상 식별:

| Smell                | 신호                      | 해결                    |
| -------------------- | ------------------------- | ----------------------- |
| **중복 코드**        | 같은 로직이 2곳 이상      | 함수/훅으로 추출        |
| **긴 함수**          | 30줄 이상, 여러 책임      | 단일 책임으로 분리      |
| **깊은 중첩**        | 3단계 이상 if/for         | early return, 함수 추출 |
| **매직 넘버**        | `if (status === 3)`       | 상수/enum으로 추출      |
| **거대 컴포넌트**    | 200줄 이상 TSX            | 하위 컴포넌트로 분리    |
| **props 드릴링**     | 3단계 이상 props 전달     | Context, Zustand store  |
| **dead code**        | 사용하지 않는 함수/변수   | 삭제 (주석 처리 금지)   |
| **과도한 추상화**    | 한 곳에서만 쓰는 유틸리티 | 인라인으로 되돌리기     |
| **일관성 없는 패턴** | 같은 일을 다른 방식으로   | 하나의 패턴으로 통일    |

## Refactoring vs Rewriting 판단

| 조건                      | 리팩토링                     | 재작성       |
| ------------------------- | ---------------------------- | ------------ |
| 테스트가 있음             | O                            | O            |
| 테스트가 없음             | 테스트 먼저 추가 후 리팩토링 | 가능 (TDD로) |
| 구조는 괜찮고 세부만 문제 | O                            | X            |
| 근본 설계가 잘못됨        | X                            | O            |
| 변경 범위가 파일 1-3개    | O                            | X            |
| 변경 범위가 모듈 전체     | 검토 필요                    | 검토 필요    |

## Red Flags — STOP

- 리팩토링과 기능 변경을 동시에 진행
- 테스트 없이 리팩토링
- "여기 온 김에" 범위 확대
- 테스트 실패를 무시하고 다음 리팩토링 진행
- 공개 API를 경고 없이 변경
- "나중에 테스트 고치면 되지" 발언

## Quick Reference

```
1. 테스트 전부 통과 확인
2. 하나의 리팩토링 수행
3. 테스트 재실행
4. 통과 → 커밋 → 다음 리팩토링
   실패 → 롤백 또는 수정
5. 반복
```
