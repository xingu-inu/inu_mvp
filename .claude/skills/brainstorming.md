# Brainstorming

## Iron Law

```
NO IMPLEMENTATION WITHOUT DESIGN APPROVAL
```

"간단해 보여도" 설계는 필수. 간단한 프로젝트에서 검증 안 된 가정이 가장 많은 낭비를 만듦.

## When to Use

- 새 기능/컴포넌트 생성 전
- 기존 기능의 동작을 변경할 때
- 아키텍처 결정이 필요할 때
- "이렇게 하면 되지 않을까?" 싶을 때

## The Process

### 1. 프로젝트 컨텍스트 파악

- 관련 파일, 문서, 최근 커밋 확인
- `docs/plan/screens/`, `docs/plan/components/` 탐색
- 기존 패턴과 컨벤션 파악

### 2. 질문으로 의도 파악

- **한 번에 하나의 질문** — 여러 질문으로 압도하지 않기
- 가능하면 객관식 질문 선호 (답변 쉬움)
- 집중: 목적, 제약조건, 성공 기준

### 3. 2-3가지 접근법 제시

- 각 접근법의 트레이드오프 설명
- 추천 옵션을 먼저 제시 + 이유
- YAGNI 적용: 불필요한 기능은 모든 설계에서 제거

### 4. 설계 제시 및 승인

- 복잡도에 비례해서 각 섹션 설명
  - 간단: 몇 문장
  - 복잡: 아키텍처, 컴포넌트, 데이터 흐름, 에러 처리
- 각 섹션 후 확인: "여기까지 괜찮나요?"
- 승인 받은 후에만 구현 진행

### 5. 구현 전환

설계 승인 후:

- 구현 계획 수립 (TodoWrite 활용)
- TDD 사이클로 구현 시작

## Key Principles

| 원칙                | 설명                           |
| ------------------- | ------------------------------ |
| 한 번에 하나의 질문 | 여러 질문 = 압도감             |
| 객관식 선호         | 개방형보다 답변 쉬움           |
| YAGNI 철저          | 불필요한 기능 설계에서 제거    |
| 대안 탐색           | 항상 2-3개 접근법 비교 후 결정 |
| 점진적 검증         | 설계 제시 → 승인 → 다음 섹션   |
| 유연성              | 맞지 않으면 돌아가서 재탐색    |

## Anti-Patterns

| 안티패턴                    | 문제                   | 해결                 |
| --------------------------- | ---------------------- | -------------------- |
| "너무 간단해서 설계 불필요" | 검증 안 된 가정 = 낭비 | 짧아도 설계는 필수   |
| 한 번에 5개 질문            | 유저 압도              | 하나씩               |
| 접근법 1개만 제시           | 편향, 대안 미검토      | 최소 2-3개 비교      |
| 승인 없이 구현 시작         | 방향 불일치 → 재작업   | 반드시 승인 후 구현  |
| 과도한 설계                 | Analysis paralysis     | 복잡도에 비례한 설계 |

## Quick Reference

```
1. 컨텍스트 파악 (파일, 문서, 패턴)
2. 질문으로 의도 파악 (하나씩)
3. 2-3 접근법 + 추천 제시
4. 설계 제시 → 유저 승인
5. 승인 후 구현 시작
```
